## 0. 结论先说

**能做，而且技术上没有硬障碍。** 但当前程序是「单文件绿色 exe、无安装器、无服务端、无版本号真源」的形态，
所以这不是「加个按钮 + 一个 HTTP 请求」的事，本质上是**给产品补一条发布通道**（版本管理 → 制品托管 → 客户端检查 → 下载 → 替换 → 回滚）。

有 3 个必须先解决的前置问题，否则做出来会出事：

| # | 问题 | 现状 | 后果 |
|---|------|------|------|
| 1 | **版本号没有唯一真源** | `WpfApp1.csproj` = `2.0.0`；exe 的 `FileVersion` = `2.0.0.0`；首页徽标写死 `v2.3.8`；`docs/程序说明.md` 记 `v2.3.5` | 拿哪个值去比较都不对：轻则永远提示更新（循环），重则漏掉更新或误判为降级 |
| 2 | **单文件 exe 运行时不能自覆盖** | `PublishSingleFile=true` + 自包含，exe 运行时被系统映射占用 | 主程序无法把自己替换掉，必须由**独立进程**在主程序退出后完成替换 |
| 3 | **exe 未签名** | 实测 `Get-AuthenticodeSignature` = `NotSigned` | 下载的新 exe 带 MOTW，SmartScreen / 杀软可能拦截；也无法验证服务端是否被篡改 |

另外 3 个会影响设计、但不阻塞的约束：

- **70 MB 全量包**：实测 exe 69.8 MB，且 `EnableCompressionInSingleFile=true`。单文件内部已压缩，二次压缩收益很小；**压缩流会让二进制差分（bsdiff 类）大面积失效**，差分更新很可能退化为接近全量，需实测后再决定要不要做差分。
- **配置写在程序目录**：`settings.json`、`invoice_templates.json`、`invoice_print_history.json` 在 exe 同目录；便签与 WebView2 缓存已在 `%LOCALAPPDATA%\CCToolbox\`。这一点直接决定选型（见 §3）。
- **客户现场可能是内网**：README 明确「核心文件处理在本地完成」，这是实施现场工具。在线更新方案必须覆盖「无公网 / 只有内网文件服务器」的场景，不能只设计公网 CDN。

## 2. 关键约束的技术分析

### 2.1 为什么必须引入独立 updater

Windows 上正在运行的 exe 不能删除或覆盖（可以重命名，但删不掉，且多实例时更乱）。
本程序还会拉起 WebView2 子进程（`msedgewebview2.exe`），单文件 exe 也会把 native 库自解压到临时目录。
所以稳妥做法是：

```text
主程序：检查 → 下载 → 校验 → 提示「退出并更新」→ 完全退出
updater.exe（独立小进程）：等待主进程 + 子进程树退出
  → 备份旧 exe → 原子替换 → 启动新 exe → 健康检查 → 自清理
```

`MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` 需要重启电脑，体验差，不推荐。

### 2.2 为什么差分更新要谨慎

`EnableCompressionInSingleFile=true` 会把托管程序集压进一条压缩流。源码改一行，压缩流后面大部分字节都会变，
bsdiff / xdelta 这类二进制差分很难找到可复用的长匹配。**velopack / Squirrel 的 delta 包对这种产物可能接近全量**。

如果确实需要差分，先做这两个实验，用数据决策：

1. 关掉 `EnableCompressionInSingleFile` 再发布（体积会明显涨，可能 150 MB+），对两个版本做 bsdiff，看补丁大小；
2. 或改回「目录发布 + 小启动器」，让差分作用在**未压缩的单个 dll** 上（差分效果最稳，但失去绿色单文件的便利）。

在没实测之前，**按每次 70 MB 全量来设计**是安全假设。带宽估算（理论值，不含开销）：
100 Mbps ≈ 6 秒；10 Mbps ≈ 1 分钟；4 Mbps ≈ 2.5 分钟。1000 台设备更新一次 = 约 70 GB 出流量。

### 2.3 配置目录是选型的分水岭

| 方案 | 配置兼容性 |
|------|-----------|
| 原地替换 exe（方案 A） | 只换 exe，程序目录内 3 个 JSON **原样保留**，零迁移成本 ✅ |
| 版本化目录 / 安装器（方案 B Velopack） | 每次升级切到 `app-2.3.9\` 新目录，旧目录里的 `settings.json` 等**看起来丢了** ⚠️ 必须先把用户数据迁到 `%LOCALAPPDATA%\CCToolbox\` |

这不是小细节：**如果直接上 Velopack 而不迁移配置，用户每次更新都会丢打印模板和设置**。

## 3. 方案选型

| 方案 | 做法 | 改动面 | 差分 | 免 UAC | 内网可用 | 评价 |
|------|------|--------|------|--------|---------|------|
| **A. 自建清单 + 全量替换 + 独立 updater** ★ | 静态 `latest.json` + 版本化 exe；客户端检查/下载/校验；独立 updater 替换并回滚 | 中（新增 UpdateService + updater 小工具 + UI 挂点） | 否（70 MB 全量） | 是（装用户目录） | ✅ 可直接指 UNC 共享 | **最贴合现状**：保留绿色单文件、配置零迁移、完全可控、无第三方依赖 |
| **B. Velopack**（Squirrel 现代继任者）★ | NuGet `Velopack` + 启动引导 + `vpk pack` 产出 full/delta 包、Setup.exe、`releases.{channel}.json`，静态托管即可 | 中（SDK 接入 + 发布流程改造 + **配置迁移**） | ✅ 官方支持 | ✅ 每用户 LocalAppData 安装 | ✅ 静态文件/文件服务器 | **能力最完整**：安装器、增量、渠道、回滚、卸载都现成；代价是要改安装形态 |
| C. AutoUpdater.NET / NetSparkle | 引一个库读 XML/RSS 清单，弹出更新框，下载后启动安装包 | 小 | 否 | 视安装器 | 部分 | 最省事，但只解决「提示 + 拉起安装器」，替换/回滚仍要自己兜底 |
| D. ClickOnce | VS 发布 ClickOnce 清单，运行时自动检查 | 大（发布形态改造） | 按文件 | ✅ | 文件共享可 | 微软文档确认支持 WPF 自动更新，但 .NET 7+ 无 `ApplicationDeployment` 等价 API，且**与自包含单文件不匹配**，老技术栈，不推荐 |
| E. MSIX + AppInstaller | 打包 MSIX，`.appinstaller` 定期检查 | 大（打包 + 签名 + 分发） | ✅ 系统级 | ✅ | 需内网托管 | 企业统一分发最规范，但要求代码签名证书与打包改造，对个人/小团队偏重 |
| F. 半自动（只检查，不在线替换） | 启动时读 `latest.json`，有新版就弹窗 + 打开下载页 / 复制下载链接 | **极小** | — | — | ✅ | 最低成本先上线「检查更新」，把「自动替换」留到下一期 |

### 推荐路线（按投入分两期）

```text
第 0 期（零代码，先做基建）：统一版本号 → 搭制品托管 → 发布脚本产出 latest.json + SHA256 → 申请代码签名证书
第 1 期：方案 A（或先上 F 验证通道），把「检查更新 + 在线替换 + 回滚」跑通
第 2 期：若更新频率高 / 用户量大 / 带宽敏感，再评估 Velopack 与差分（务必先完成配置迁移）
```

**决策捷径**：
- 想保持「一个 exe 拷来拷去」的绿色形态、客户多在内网 → **A**
- 愿意引入安装器、想一次拿到增量/渠道/卸载/回滚 → **B**
- 只想先让用户知道「有新版本」→ **F**

## 4. 方案 A 详细设计（推荐起步）

### 4.1 服务端：纯静态文件，不需要写任何后端

```text
/updates/
└── stable/
    ├── latest.json                      # 入口清单，短缓存 / no-cache
    ├── 2.3.8/CCToolbox.exe
    ├── 2.3.9/CCToolbox.exe
    └── CHANGELOG.md
└── beta/
    └── latest.json                      # 同上，供测试通道
```

托管方式任选：Nginx / 对象存储（COS、OSS）/ GitHub Releases / 内网 IIS / **UNC 共享目录 `\\server\share\updates\`**。
内网场景可以直接把 `UpdateUrl` 配成 UNC 路径，用文件复制代替 HTTP，连 Web 服务都不用搭。

`latest.json` 建议字段（数据契约，非代码）：

```json
{
  "schema": 1,
  "product": "CCToolbox",
  "channel": "stable",
  "version": "2.3.9",
  "releaseDate": "2026-11-05",
  "minimumVersion": "2.3.0",
  "mandatory": false,
  "rolloutPercent": 100,
  "package": {
    "url": "https://example.com/updates/stable/2.3.9/CCToolbox.exe",
    "size": 73183200,
    "sha256": "<64位十六进制>",
    "rid": "win-x64",
    "requiresDotnet": false,
    "requiresWebView2Runtime": true
  },
  "changelogUrl": "https://example.com/updates/stable/CHANGELOG.md",
  "changelog": ["新增 XXX", "修复 YYY"]
}
```

字段用途：
- `version`：三段 SemVer，与 csproj `<Version>` 完全一致，四段数值比较，**禁止降级**。
- `minimumVersion` / `mandatory`：低于最低版本时强制更新（修严重 bug / 数据错误时用），否则允许「稍后 / 跳过此版本」。
- `rolloutPercent`：配合稳定匿名机器 ID 取模做灰度，先放 10% 再全量；也可简化为 stable/beta 两个清单。
- `sha256`：下载后必须校验，防止传输损坏或镜像被换包。
- 清单本身建议再做一层 RSA 签名（或至少全链路 HTTPS + 域名校验），防止「清单被篡改 → 指向恶意 exe」。

### 4.2 客户端模块划分（职责，不含实现）

| 模块 | 职责 | 现状挂点 |
|------|------|---------|
| `VersionInfo` | 从程序集读当前版本（唯一真源），不再读首页写死文本 | 新增；首页 `TxtVersionBadge` 改为绑定它 |
| `UpdateChecker` | 启动后延迟静默检查 / 手动检查 / 定时检查；比较版本、灰度、强制策略、解析清单 | 新增；`App.OnStartup` 里挂一个延迟异步任务 |
| `UpdateDownloader` | 后台下载到 `%LOCALAPPDATA%\CCToolbox\updates\<ver>\`，进度/取消/重试/Range 续传/SHA256 校验 | 新增 |
| `Updater.exe` | 独立进程：等待退出 → 备份 → 替换 → 启动 → 健康检查 → 回滚 | **新增的独立小工具**，不进主程序 |
| UI | 首页版本卡片加「检查更新」角标；设置页加「自动检查 / 通道 / 忽略此版本 / 更新日志」 | 现成页面，最小改动 |
| `UpdateLog` | 写 `%LOCALAPPDATA%\CCToolbox\logs\update.log` | 便于现场排障 |

### 4.3 时序

```text
① 启动 → App.OnStartup 注册单实例 Mutex；延迟 3~5s 起低优先级静默检查
      （断网/超时/解析失败一律静默，不弹窗、不阻塞主窗口）
② 手动点「检查更新」 → 必须给明确反馈：已是最新 / 发现新版 / 检查失败
③ GET latest.json（加时间戳参数防 CDN 缓存）→ 版本比较 → 灰度判定
④ 有新版 → 展示版本号 + 更新日志 + 包大小 → [立即更新] [稍后] [跳过此版本]
⑤ 下载到临时目录 .partial → SHA256 校验 → 改名为目标文件名
⑥ 提示「需要重启完成更新，请先保存当前工作」
      ⚠️ 程序有便签（关闭窗口才自动保存）、CSV 对比进程内状态、正在进行的打印任务，
         不能在用户无感知的情况下强杀进程
⑦ 用户确认 → 主程序启动 Updater.exe（带参数：新包路径、目标路径、备份路径、原命令行）→ 主程序退出
⑧ Updater 等待主进程 + WebView2 子进程树完全退出（超时给明确提示）
      → CCToolbox.exe → CCToolbox.exe.bak
      → 新包写入 CCToolbox.exe
      → 写 .pending-update 标记（旧版本路径、备份路径、时间）
      → 启动新 exe
⑨ 新版本 MainWindow 显示成功后删除 .pending-update，并清理 .bak（保留最近 1 份即可）
⑩ 若新进程启动后立刻崩溃 / 超时未清除标记 → Updater 自动恢复 .bak、删除新 exe、
    重启旧版本并写日志 → 用户回到可用状态
```

### 4.4 Updater 进程契约（建议）

```text
Updater.exe --target "<exe路径>" --source "<已校验的新包>" --backup "<bak路径>"
            --wait-pid <主进程PID> --restart-args "<原命令行>" --timeout 30
退出码：0 成功 / 1 参数或校验失败 / 2 进程未退出 / 3 替换失败（已回滚） / 4 健康检查失败（已回滚）
```

要点：
- **权限**：若程序放在 `Program Files`，替换需要管理员 → updater 需 `requireAdministrator` 清单并弹 UAC；
  更推荐安装到用户可写目录（如 `%LOCALAPPDATA%\CCToolbox\app\`），全程免 UAC。
  顺带解决现有问题：`settings.json` 写程序目录在只读目录会保存失败。
- **单实例**：无 Mutex 时两个实例同时更新会互相踩踏，必须先加命名 Mutex。
- **备份上限**：每份 70 MB，只保留最近 1~2 份，避免磁盘膨胀。
- **不碰用户数据**：只替换 exe，程序目录里的 3 个 JSON 一律不动。

### 4.5 安全清单

1. 全链路 HTTPS；内网 UNC 场景靠共享目录 ACL + 清单哈希。
2. `sha256` 强校验，校验不通过直接删除临时文件、绝不替换。
3. 版本只升不降；清单带 `releaseDate`，拒绝「未来时间 / 比已安装更旧」的清单（防回放）。
4. 给主 exe、Updater.exe 做 Authenticode 代码签名；当前 `NotSigned`，未签名的下载文件会触发 SmartScreen「Windows 已保护你的电脑」和杀软误报，这是**上线前必须解决的体验问题**。内网可用组策略 / 受信任发布者缓解。
5. 进阶：清单 RSA 签名 + 公钥内置在客户端。
6. 可选埋点只上报「版本号 / 成败 / 错误码」，且需在设置里给开关并写进说明——README 现在承诺「不上传文件」，别悄悄违背。

### 4.6 网络与失败处理

| 场景 | 策略 |
|------|------|
| 断网 / 超时 / DNS 失败 | 静默失败，记录日志，不影响任何功能；下次启动重试 |
| 下载中断 | `.partial` 保留 + HTTP Range 续传 + 指数退避重试 3 次 |
| 磁盘不足 | 下载前按 `size` 预检可用空间 |
| SHA256 不符 | 删除并重下或报错，绝不替换 |
| 进程占用 / 无写权限 | Updater 明确提示，保留旧版本可正常运行 |
| 新版本启动失败 | 自动回滚（§4.3 ⑩），写日志 |
| CDN 缓存旧清单 | `latest.json` 设 `no-cache` 或加时间戳查询参数；exe 用版本化路径可长缓存 |

### 4.7 发布流程（可脚本化，零业务代码）

```text
1) dotnet publish -c Release -p:PublishProfile=SingleFile-win-x64
2) 从 csproj 读 <Version> → 作为唯一版本号（同步首页显示）
3) Get-FileHash -Algorithm SHA256 计算 exe 哈希与字节数
4) 生成/更新 latest.json（含 changelog、minimumVersion、mandatory、rolloutPercent）
5) 上传到 /updates/stable/<version>/；先传包，最后原子替换 latest.json（避免「清单指向还不存在的包」）
6) 灰度：rolloutPercent 10 → 观察 → 100
7) 归档旧版本包，保留最近 N 个以便回滚
```

## 5. 方案 B（Velopack）落地差异

官方文档已核实的关键点：

- 接入三步：装 `Velopack` NuGet 包 → 入口调用 `VelopackApp.Build().Run()` → `UpdateManager(url)` 的 `CheckForUpdatesAsync` / `DownloadUpdatesAsync` / `ApplyUpdatesAndRestart`。
- 发布：先 `dotnet publish --self-contained -r win-x64` 到目录，再 `vpk pack --packId ... --packVersion ... --packDir ... --mainExe CCToolbox.exe`。
- 产物：`*-full.nupkg`、`*-delta.nupkg`（有上一版本时自动生成）、`*-Setup.exe`、`*-Portable.zip`、`releases.{channel}.json`、`assets.{channel}.json`。
- 托管：**任意静态文件服务**即可（云存储 / GitHub Releases / 内网文件服务器），无需后端。
- **不支持四段版本号**（如 `2.0.0.0`），必须用 semver2 三段；当前 `AssemblyVersion 2.0.0.0` 不能直接当 `packVersion` 用。
- 官方明确建议分发前做代码签名，否则可能无法运行。
- Windows 按用户安装到 LocalAppData、免管理员，并提供 Portable 形态（对「绿色工具」较友好）。

**落地前必须处理的 3 件事**：

1. **配置迁移**：把 `settings.json` / `invoice_templates.json` / `invoice_print_history.json` 从程序目录迁到 `%LOCALAPPDATA%\CCToolbox\`，并做一次性旧数据导入。否则版本目录一切换，用户设置与打印模板就「消失」。
2. **单文件与压缩**：官方文档推荐自包含目录发布；现有「压缩单文件」能否稳定命中 delta 需实测（见 §2.2），必要时关掉 `EnableCompressionInSingleFile` 或改为目录发布。
3. **发布形态改变**：从「一个 exe」变成「Setup.exe + 版本目录 + 快捷方式」，要给现有用户设计一次迁移（首次安装时导入旧配置、提示卸载/删除旧 exe）。

## 6. 内网 / 离线场景（本产品重点）

实施现场很可能没有公网，方案必须能降级：

| 通道 | 实现 |
|------|------|
| 内网 HTTP | `UpdateUrl` 指向内网 Nginx/IIS，其余流程不变 |
| 内网共享目录 | `UpdateUrl` 指向 `\\server\share\updates\latest.json`，用文件复制代替 HTTP，无需任何服务 |
| 完全离线 | 提供「离线更新包」：把 `<version>/CCToolbox.exe` + `latest.json` 放 U 盘，设置页允许手动指定清单/包路径，走同一套校验与替换流程 |
| 无任何更新源 | 检查静默失败；手动检查明确提示「无法连接更新服务器」，并提供「手动下载」入口 |

建议把 `UpdateUrl`、通道、自动检查开关都做成 `settings.json` 里的可配置项，方便现场实施人员按需改。

## 8. 验收测试矩阵

| 用例 | 期望 |
|------|------|
| 断网启动 / 更新源超时 | 静默失败，主功能完全可用，日志有记录 |
| 已是最新 / 有新版 / 强制更新 / 跳过此版本 | 四种分支提示正确，不重复打扰 |
| 服务端版本低于本地（降级/回放） | 拒绝，不提示 |
| 下载中断后续传、校验失败、磁盘不足 | 不产生半包、不替换、旧版本仍可运行 |
| 更新时程序多开、WebView2 子进程仍在 | 阻止或等待，不出现「文件被占用」 |
| 装在 Program Files / 只读目录 | 要么正确提权，要么明确提示，不静默失败 |

| 更新后检查 `settings.json` / 打印模板 / 打印历史 / 便签 | 全部保留（方案 A 应零变化） |
| 未签名 → 已签名对比 | SmartScreen / 杀软不误拦 |

## 9. 风险与取舍

| 风险 | 说明 | 缓解 |
|------|------|------|
| 70 MB 全量下载 | 每次更新流量与等待明显 | 差分实测；错峰下载；内网共享；只提示不强制下载 |
| 未签名导致拦截 | 当前 exe `NotSigned` | 上线前签代码签名证书；内网用受信任发布者策略 |
| 配置丢失 | 方案 B 版本目录切换 | 先迁到 `%LOCALAPPDATA%` 并做导入 |
| 更新打断用户工作 | 便签、CSV 状态、打印任务都是进程内状态 | 一律「确认后重启」，不静默强杀 |
| 升级失败变砖 | 替换环节最容易出问题 | 备份 + pending 标记 + 自动回滚 + 日志 |
| 清单被篡改 | 指向恶意包 | HTTPS + SHA256 + 版本防回放 + 可选 RSA 签名清单 |
| 引入第三方框架 | Velopack 带来长期维护依赖 | 先在分支做 POC，验证单文件压缩下的 delta 命中率再决定 |

## 10. 一句话建议

**先把版本号统一和制品托管这两件零代码的事做掉，然后按方案 A 落地「清单 + SHA256 + 独立 updater + 自动回滚」**——
它保留你现在「一个 exe 绿色分发、配置不动、内网可用」的全部优点，改动面可控；等更新频率真的高到 70 MB 成为瓶颈，再评估 Velopack 与差分。
